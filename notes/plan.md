### 2. 第一版的固定范围

- C++17、Linux、CMake。
- 单线程 Reactor、非阻塞 Socket、epoll LT；一个 EventLoop 管理监听和客户端连接。
- 网络层保留 EventLoop、Channel、Acceptor、TcpConnection、Buffer；用 RAII 和明确的所有权管理资源。
- HTTP 层保留请求、响应、解析器和服务器的职责划分。
- 接口只做 `GET /health` 和 `POST /echo`，未知路径返回 404。
- 实现 HTTP/1.1 的有限子集：请求行、Header、Content-Length 定长 Body、持久连接及同连接顺序响应。
- 不支持的 Transfer-Encoding、非法或不明确的请求长度等输入，明确拒绝并关闭，不能误当成下一个请求。
- 设置基本 Header、Body 大小上限，避免无限积累超大请求；具体值写进 README。

线程池、主从 Reactor、ET、定时器和完整日志库不属于第一版要求。现有简历没有承诺这些能力，可以后置学习。

### 4. 按四个交付步骤推进

#### A. TCP Echo 基线

实现网络层组件，跑通接受连接、读取、回写和关闭。监听 Socket 与客户端 Socket 都采用非阻塞模式。

需要明确处理 `EINTR`、`EAGAIN/EWOULDBLOCK`、EOF 和不可恢复错误；单个客户端断开不能导致服务器退出。关闭时注销事件并安全释放对象，避免事件回调访问已销毁的连接或 Channel。

完成标准：多个客户端可以连接、收发和断开；能解释 `epoll → EventLoop → Channel → 回调` 的执行过程。

#### B. HTTP 基线与增量解析

接入 `/health`、`/echo`，构造带正确状态行、Header、Content-Length 和 Body 的响应。

解析器明确返回三种结果：

```cpp
enum class ParseResult { NeedMoreData, Complete, BadRequest };
```

必须实现：

- 请求行、Header、Body 跨多次接收时保留解析进度和未消费数据。
- 按 Content-Length 精确消费 Body，不能把下一条请求吞进当前 Body。
- 一次接收多个请求时循环解析，按请求顺序生成响应。
- 完成一个请求后重置对应解析状态，保留后续字节；数据不足时继续等待。
- 非法请求明确报错，不能把“尚未收完”当作非法。

完成标准：普通 curl 请求通过，分段请求和连续请求测试通过。

#### C. 非阻塞发送与连接收尾

先尝试发送，未发送部分进入 Output Buffer；有积压时监听 EPOLLOUT，可写时继续发送，缓冲清空后取消写事件。

必须实现：

- 短写只消费实际发送的字节，后续响应追加到已有输出之后，保持顺序。
- `EINTR` 重试；`EAGAIN/EWOULDBLOCK` 保存剩余数据并等待可写事件。
- 客户端异常断开时安全收尾，避免 SIGPIPE 终止服务器。
- `Connection: close` 等主动关闭场景，等待响应发送完成后再关闭。
- 对端关闭发送方向时，先处理已收到的数据和待发送响应，再决定释放时机。
- 重复关闭不会重复释放；当前批次事件处理结束前，相关对象的生命周期仍然有效。

完成标准：慢客户端最终收到完整响应；提前断开的客户端不导致崩溃；发送完成后没有无效写事件造成忙循环。

#### D. 最小测试、检查与说明

测试跟随 B、C 一起实现，最后统一验收。可以用 C++ 测试解析器和 Buffer，用 Python socket 脚本验证真实网络行为。

| 场景 | 至少验证什么 |
| --- | --- |
| 普通请求 | `/health`、`/echo`、404；按响应长度核对完整内容 |
| 分段请求 | 请求行、Header、Body 分段；解析器覆盖不同切分点及逐字节输入 |
| 连续请求 | 一次发送两个请求，得到两个顺序正确、边界明确的响应 |
| Buffer 边界 | 部分消费、恰好消费全部、再次追加、包含零字节的数据 |
| 慢客户端 | 大 Echo 响应、缩小发送缓冲、客户端暂不读取；观察短写或 EAGAIN，再确认完整收取 |
| 异常断连 | 未收完请求时断开、发送响应时断开；随后新客户端仍能正常请求 |
| 关闭流程 | 响应发送完成后关闭、对端半关闭、重复关闭不会崩溃或丢响应 |

慢客户端测试需要实际进入输出缓冲和等待写事件的路径，可以通过计数或调试记录确认；普通小响应测试不能替代它。分段网络发送不保证对应相同的 read 边界，因此解析器测试也必须直接输入不同片段。

用 ASan/UBSan 构建并运行适用的单元及网络测试，处理发现的问题，保留命令和结果。检查通过仅表示这些场景未发现相应问题，不能据此宣称已经证明没有缺陷。

README 至少写明：构建运行命令、两个接口、协议支持范围、测试与 Sanitizer 命令、教程来源和个人改动。

- 保存参考来源和每次个人修改；只有实际复现、修改、验证过的问题，才作为个人贡献介绍。
- 每完成一项，能说清楚输入、状态变化、错误路径和测试依据，再进入下一项。

## 二、投递后：把小版本完善为小而精的 Server

投递后主要补正确性、证据和解释能力。接口范围继续保持 `/health`、`/echo`，围绕同一条网络与 HTTP 链路深入。

### 1. 先加深已有边界测试

- 增加不同切分点、不同 Body 长度、二进制 Body，以及多个连续请求的组合测试。
- 补非法请求长度、重复长度字段、超限请求、完整请求后接半个请求等输入；明确拒绝规则。
- 用可控的 I/O 测试验证 EINTR、短写和 EAGAIN，避免依赖偶然出现的网络行为。
- 重复连接与断开、对端 RST、半关闭、发送期间请求关闭，检查资源释放和事件注销。
- 让慢客户端与普通客户端同时工作，确认慢连接不会阻塞整个 EventLoop。

每次按“复现问题 → 分析原因 → 修改 → 回归验证”推进，保留少量有价值的调试记录。

### 2. 完善 Buffer、生命周期和资源边界

- 根据真实测试检查 Buffer 消费、扩容、压缩及输出追加行为，测量后再优化拷贝和分配。
- 梳理连接所有权、回调捕获和延迟释放，说明 fd、Channel、TcpConnection 的关闭顺序。
- 在初版请求大小限制基础上，补连接数和待发送数据上限；必要时增加读取暂停与恢复，控制慢客户端造成的输出积压。
- 若测试显示空闲连接长期占用资源，再考虑一个简单超时机制，并测试它与正常发送、关闭流程的交互。

这些改进服务于已经存在的问题；复杂 Timer、完整日志系统没有默认加入计划。

### 3. 做真实、可复现的 Benchmark

正确性稳定后，再参考 Day 30 和合适的压测工具。记录：

- 环境、构建类型、测试命令、接口与响应大小、连接复用方式。
- 并发连接数、测试时长、成功请求吞吐、错误率。
- P95/P99 延迟（采用确实能提供这些统计的工具）、CPU 和内存占用。

建立单线程基线；做优化时固定环境和负载，比较修改前后数据。只有实测结果才写入 README 或简历，不预设万级 QPS 或性能提升比例。

线程池、主从 Reactor、ET 可以继续学习，但只有在发现明确瓶颈、理解新增复杂度后，才考虑选一项实现，并用相同测试和压测验证。完成一个可靠的单线程版本也可以作为项目终点。

### 5. 最终完成标准与范围控制

项目达到以下状态，就可以收尾：

1. 核心请求链路完整，支持范围明确。
2. 增量解析、非阻塞发送、Buffer 和关闭边界有回归测试。
